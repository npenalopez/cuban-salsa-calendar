1. Top issues

Five problems matter more than any visual change. The first two are not design issues, but you asked me to push back where needed.

P0 · SECURITY Any visitor's browser can overwrite the database On load, when the stored version differs, the app calls replaceFestivals() against Supabase with the public anon key. That only works if anonymous users are allowed to write and delete, so anyone can wipe the table from devtools. The admin password is also hard-coded in PasswordProtection.tsx and ships in the JS bundle. Hiding it behind 4 clicks on the title does not protect it.
P0 · DATA 19 festivals are silently hidden Dates like TBC 2026, TBA 2026, TBC March 2026 don't parse to a month, so isDisplayableFestival drops them. They never appear, not even as "date TBA". A festival marked (POSTPONED) is shown as a normal upcoming event because the parser strips parentheses.
P0 · LINKS The main button often leads to a made-up URL 105 of 147 festivals have no Instagram handle. getInstagramUrl() then guesses instagram.com/{festival.id} (e.g. /afro-cuban-berlin-2026), which is almost always a 404 or a stranger's account. On mobile this is the primary CTA.
P0 · ORDER Mobile list is in the wrong order Below 1024px, FestivalCalendar groups by month name only and iterates January→December. Today that puts January 2027 at the top and October 2026 near the bottom, and would merge two years of the same month into one section. Desktop groups by month + year and is correct.
P1 · REACH Nothing exists without JavaScript No per-festival URLs, no real <a href> links anywhere (every link is window.open on a button), no Open Graph tags. Links shared on Instagram or WhatsApp preview as blank. See section 5.

3. Data model

16 fields, all present on all 147 records. "Filled" counts values that aren't empty, -, or [].

FieldTypeFilledFindings
idstring147Slug with year (afro-cuban-berlin-2026). Unique. Good base for URLs.
namestring147Recurring festivals appear as separate records per edition (Mi Habana Baila Oct 2026 + Apr 2027) with nothing linking them.
citystring147OK.
countrystring14743 values. Asia (TBC) is not a country. USA vs "United States" naming isn't standardised; flags are resolved by name lookup. No ISO code.
continentstring1476 values; derivable from country, so it can drift. Cuba, Mexico and the Dominican Republic are "North America", which dancers are unlikely to guess when filtering.
datesfree text147The biggest problem. 13 formats. 110 are Month D-D, YYYY; 8 cross-month; 8 month-only (Early November 2026) where the date badge shows "2026" as the day and duration shows "1 day"; 19 year-only (TBC 2026) that are hidden; status stuffed into text ((POSTPONED), (Fall Edition)). A ~1,400-line regex parser (dateUtils.ts) exists to interpret this and still defaults undated years to 2025.
pricefree text22 real125 are the literal TBA (not the - the code checks for). The other 22 mix currencies and formats: Full Pass from €80, 80,000-490,000 COP, €150 / €330 with hotel. Not sortable or comparable. soldout is a magic string, used 0 times.
websiteurl24No separate ticket or pass link, which is what you need for revenue.
instagramurl42All full URLs (good). 2 point to posts (/p/…), not profiles. 105 festivals have neither website nor Instagram.
descriptionstring14762 contain editorial notes meant for you ("User to verify…", "Details carried over from the 2026 entry; verify…"). Not shown on cards, but exported into users' calendars.
artistsstring[]38203 unique names. Spelling variants split identities: Yusimi Moya Rodriguez / Rodríguez, Seo Fernandez / Fernández, Jonar Gonzalez / González, Lorenys Rodriguez / Rodríguez, DJ Jack El / el Calvo. DJs are identified by a "DJ" prefix only; no role field.
coordinates[lat, lng]147All valid, city-level. A map view is cheap because of this.
venue, category, yearsActivestring0Never filled. category is still a required field in the admin "complete" check, so every record is flagged incomplete.
monthsstring[]147Derived from dates and recomputed on load. Redundant in the file.

Missing fields, needed for the features you listed

  • startDate / endDate (ISO, nullable) + datePrecision (day | month | year). Keep the human text only as an optional override. This alone removes most of dateUtils.ts.
  • status: scheduled | dates-tba | postponed | cancelled | sold-out.
  • ticketUrl (for "Get passes"; allows an affiliate link separate from the website).
  • priceFrom (number) + currency (ISO 4217), keeping priceNote as text.
  • series id to link editions of the same festival across years.
  • styles (salsa cubana, timba, rumba, son, afro-cuban, reggaeton…) — useful for filtering since many festivals are mixed.
  • lastVerified date, shown to users as trust signal.
  • notes (private): move editorial notes out of description.
  • countryCode (ISO 3166) for flags, region grouping, and schema.org.
  • featured (future sponsored listings), image (link previews).

It stays one flat JSON file you edit by hand. I'll propose the exact schema and a one-time migration script in Phase 2; the script converts all 147 records and lists the ones it couldn't parse for you to check.

4. Design audit

Severity: P0 broken or blocking · P1 significant · P2 moderate · P3 polish

4.1 Visual hierarchy and scannability

  • P0Mobile month order and missing years (see top issues). You can't plan a trip from a list that isn't chronological.
  • P1On mobile, the date is the smallest and right-most element of the card (a 3em badge), and the name is ~14px. Date and city are what people scan for; they should lead the card.
  • P1On a 375 × 667 phone, the header, masthead, search, chips and fun-facts card stack to roughly 700px before the first festival. The first screen shows no festival.
  • P185% of prices and 74% of line-ups are unknown, and both are shown as coloured badges ("Price to be announced" amber, "Artists to be announced" amber box). Missing info gets more visual weight than real info. Unknowns should recede.
  • P2Each mobile card has two stacked full-width buttons (~100px). Across 122 cards that's a lot of scroll spent on buttons, and every card has an identical visual weight, so nothing stands out.
  • P2The fun-facts carousel sits between the filters and the results, so it separates the controls from what they control. It's also the only animated element on the page.
  • P3Continent repeated on every card; duration badge for month-only dates reads "1 day".

4.2 Consistency

  • P1Two unrelated card components switch at 1024px, with different layouts, CTA labels ("Instagram" vs "View festival"), link logic, and artist display. Resize the window and the product changes.
  • P1globals.css has ~2,000 lines of overrides, many !important and aimed at Tailwind class combinations (.flex.items-start.gap-2\.5). The global button{min-height:44px} is what breaks the carousel dots. Any change to a class name silently changes layout elsewhere.
  • P2Type: mobile card uses inline em sizes (0.675em, 0.75em, 0.875em) while the rest uses Tailwind px sizes. No type scale.
  • P2Colour: the brand gradient, plus unrelated blue / green / purple / red icons in search suggestions, amber and red badges, gold/silver/bronze podium. Secondary buttons are black-bordered on mobile and gray-bordered on desktop.
  • P2Copy: English is hard-coded in "View festival", "Sort", "Region", "Fun facts", "Top Artists", "Choose Calendar", all toasts. In German the page mixes two languages.
  • P3Radii mix rounded-md, rounded-lg, rounded-full without a rule. Two display fonts load (Inter + Bricolage Grotesque) via blocking CSS @import.

4.3 Accessibility (WCAG 2.1 AA)

  • P11.4.3 Contrast. White text on the gradient: 2.9:1 at the orange end (#ff6a3d), 4.3:1 at the red end (#e23744). Both fail for 14px text; used on every primary button and active chip. gray-400 (#9ca3af, 2.5:1) is used for years, chip counts, the footer and search categories.
  • P14.1.2 / 2.1.1. No real links. The desktop row is a div role="link" containing buttons (nested interactive). Users can't open in a new tab, long-press to copy, or see the destination.
  • P12.2.2 Pause. Carousel auto-advances; pausing only works with a mouse hover. No pause for keyboard, touch or screen readers.
  • P12.1.1 / 1.4.13. Desktop artist list opens on mouse hover only. The line-up can't be reached by keyboard or touch.
  • P14.1.2 Search. The autocomplete has no role="combobox", aria-expanded, aria-controls or aria-activedescendant; arrow-key focus is visual only, so screen readers announce nothing.
  • P24.1.2 Names and states. The region button has no accessible name on mobile (its label is hidden below 640px). Month chips have no aria-pressed; selection is shown by colour only. The date badge's aria-label sits on a plain div and is ignored.
  • P22.4.7 Focus visible. Most custom buttons (chips, header icons, carousel) have hover styles but no focus style.
  • P2Target size. Carousel arrows are 28px; the dots are 6px wide. The 44px global rule fixes height but not width and breaks layout. (2.5.5 is AAA, but 24px is the 2.2 AA minimum and the practical floor.)
  • P2A location permission prompt and a modal both appear within 1.5 s of the first visit, before the user has done anything. Native alert/confirm/prompt are used as calendar fallbacks.
  • P3Heading outline: the h1 is the wordmark; the hero is an h2 alongside month h2s. Help-page tabs are icon-only on mobile.

4.4 Responsiveness

  • P1The layout is desktop-first in practice: mobile got a separate, older component rather than a mobile version of one card. Tablets (640–1023px) get a 2-column grid of mobile cards.
  • P2Two sticky bars (header 56px + chips/sort, which wrap to two rows under 1024px ≈ 90px) take ~22% of a 667px screen while scrolling.
  • P3Kept as-is: 16px search input (prevents iOS zoom), bottom sheet for rankings, horizontal chip scroll. These are good.

4.5 Missing states

  • P0Dates to be announced: not a state at all; those festivals vanish.
  • P1Postponed / cancelled: no state; shown as normal.
  • P1Past festivals: removed entirely. There is past-state UI, but it never renders. Dancers often check "when was it last year" to guess next year's dates, and past pages keep search traffic.
  • P2No results: exists, but offers only "Show all". It could suggest the nearest match (e.g. "Nothing in Asia in March. 2 in April").
  • P2Loading: a decorative animation and no layout skeleton, so the page jumps when data arrives. Error: falls back silently (acceptable), with no "last updated" signal. No link: no state for festivals without website or Instagram (they get the guessed URL).
  • P3Sold out: supported in code, never used in data. Location denied: handled silently (fine).

5. SEO and discoverability

What crawlers get today: <title>, a meta description ("…I hope you will find them here :)"), and an empty <div id="root">. Googlebot renders JavaScript in a delayed second pass, but other search engines render it inconsistently, and link-preview bots (WhatsApp, Instagram DMs, Facebook, iMessage, Slack) never run it. Since most of your traffic likely arrives through Instagram, the blank preview is the most visible cost. No sitemap, canonical, Open Graph, structured data, or hreflang for the 5 languages served from one URL.

A. Patch the shell Effort S Static OG/Twitter tags, a share image, better description, and a <noscript> festival list in index.html. Fixes the homepage preview only. No festival pages.
B. Static generation at build (recommended) Effort M Your data is already a JSON file in the repo, which is the ideal case. At build time, generate real HTML for /, /festivals/{id}, /country/{country}, /{year}/{month}, each with Event JSON-LD, OG tags and a sitemap. Search and filters load on top as interactive islands. Astro fits best; vite-react-ssg if you want to stay closer to the current code. Pushing a JSON change rebuilds the site in about a minute (Netlify, Vercel, Cloudflare Pages).
C. Server rendering Effort L Next.js / Remix rendering per request from a database. Only worth it if data is edited live and must appear instantly. It adds a server to maintain. Overkill for 150 records edited by one person.
D. Prerender service Effort S, ongoing cost Prerender.io-style bot detection that serves snapshots. Google now describes this as a workaround. It still needs per-festival URLs in the app to be useful.

Trade-off with B: the repo JSON becomes the single source of truth, so the in-browser admin can't publish by writing to Supabase. It can stay as an editor that exports JSON (as it does now) or commits through the GitHub API. This also resolves the P0 security issue, because the public site no longer needs write access to anything. I recommend B, with option A's tags as part of it.

On Event structured data: Google's event rich results need a real startDate. The 19 year-only festivals and 8 month-only ones should get pages without Event markup (or with eventStatus once dates are known), otherwise Search Console will flag them.

7. Decisions needed before Phase 2

  1. Baseline. Is this export the version to preserve, given the live site shows a placeholder?
  2. Security now. Check the Supabase table's Row Level Security today, independent of the redesign. If anon can insert or delete, anyone can wipe the data.
  3. Architecture. OK to move to static generation (option B), with the repo JSON as the only source of truth and Supabase removed from the public site?
  4. Admin. Keep the in-browser admin table as a JSON editor that exports (as now), or edit the JSON directly? The 4-click and password gate would be replaced by it simply not being on the public site.
  5. Data migration. OK to change the JSON shape (ISO dates, status, ticket URL, private notes)? It stays one hand-editable file.
  6. Past festivals. Show them in an archive (my recommendation), or keep hiding them?
  7. Keep or cut (each is on the contract; I won't remove any without a yes): travel-time estimates and the location prompt; fun-facts carousel; growth modal; 5 languages; Help page and its 7 tutorials.
  8. Unreachable code. Should any of the map, share, heatmap or currency components come back as features?
